## Issues to consider

1. **There is still a size ceiling.** localStorage is a few MB per origin in total. Deduplication helps a lot when icons repeat, but a library with many distinct favicons can still hit the quota. If your measurements show you are still close to the limit, the next step is moving icons to IndexedDB. The id-keyed cache maps directly onto an IndexedDB store, so this design doesn't block that.
2. **Hash choice.** I used cyrb53, a 53-bit non-cryptographic hash. A collision would show the wrong favicon but would not lose bookmarks. SHA-256 needs `crypto.subtle`, which is unavailable on plain-HTTP origins, so I avoided it.
3. **Two keys are not atomic.** Icons are written before the tree. If the tree write fails after a delete pruned an icon, the stored tree can point at a missing icon. That item shows the default globe, and nothing crashes. The orphaned data is cleaned up on the next delete.
4. **Garbage collection runs only on delete.** Append-import keeps existing icons on purpose, since they are still referenced.

## Storage limits per origin

An origin is a site, such as `http://localhost:3000`. All tabs of one origin share its quota.

**localStorage**
- The [Storage Standard](https://storage.spec.whatwg.org/) sets it at 5 MiB. Chrome, Firefox, and Safari all enforce about 5 MB ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)).
- The quota covers all keys of the origin, and writes past it throw `QuotaExceededError`.
- One source says some engines count two bytes per character, which would cut the practical limit for base64 to about 2.5 million characters. I could not confirm that in a primary source.

**IndexedDB**
- There is no fixed size. The browser picks a quota from disk size, and IndexedDB shares it with the Cache API and the Origin Private File System.
- Chrome and Edge: up to 60% of the disk per origin, and 80% across all origins. Incognito and "clear on exit" modes are much smaller.
- Firefox: best-effort data gets the smaller of 10% of the disk or 10 GiB per site. Persistent storage gets up to 50% of the disk.
- Safari 17 and later: about 60% of the disk for the browser app, and about 15% for apps that embed web content.
- Best-effort data can be evicted under disk pressure, so the browser may delete the whole origin's data. `navigator.storage.persist()` asks the browser to keep it.
- `navigator.storage.estimate()` reports approximate usage and quota. Chrome 133 and later reports the quota as usage plus 10 GiB, so the number is only a rough guide.

For this app, localStorage's roughly 5 MB is the real constraint. IndexedDB would give room for hundreds of megabytes or more.

**User**

What are the implications—in terms of pros and cons—of switching to IndexedDB?

---

**Cursor**

Switching to IndexedDB would remove the 5 MB ceiling and make writes cheaper, but it changes startup, export, and the size measurements. Those costs are real for this app.

## Pros

- **Much more room.** Quotas are set from disk size, typically hundreds of megabytes or more in desktop browsers. Chrome also allows about 5% of the disk in incognito and about 300 MB when it clears data on exit (see the [web.dev storage guide](https://web.dev/articles/storage-for-the-web)).
- **Icons can be stored as binary.** Icons are now base64 text, which is about a third larger than the image bytes. IndexedDB can store them as `Blob`s and show them through object URLs, which also keeps the large strings out of memory.
- **Atomic writes across stores.** Tree and icons can be written in one transaction. That removes the two-key ordering problem I described earlier.
- **Per-item writes.** Records can be stored one per node, so an edit writes only the changed node. Today every change re-serializes the whole tree.
- **Less blocking.** localStorage calls are synchronous and block the page. IndexedDB work runs asynchronously.

## Cons

- **Startup becomes async.** The atoms in `a-bookmarks-atoms.ts` read localStorage synchronously at module load. With IndexedDB they need a loading state or async hydration, and the first render has to handle an empty state.
- **Export becomes async.** The Netscape export needs `ICON="data:..."`. Blobs would have to be read and converted to base64 before export.
- **More code.** IndexedDB's API is verbose. Versioned schema upgrades and migration from the current localStorage keys add work. A small wrapper such as the `idb` library would reduce this.
- **Errors arrive later.** Quota failures come back as failed requests or aborted transactions. The synchronous try/catch and the "too large" notice would need reworking.
- **Writes need ordering.** Async writes can finish out of order, so they need a queue or a debounce.
- **Measurement gets coarser.** The console stats use exact character counts from localStorage. `navigator.storage.estimate()` gives only approximate usage, and Chrome reports the quota as usage plus 10 GiB. Blob sizes are exact, but the total is still approximate.
- **Private modes are tighter.** Incognito and clear-on-exit modes have much smaller limits, as noted above.
- **Both stores are best-effort.** The browser can evict data under disk pressure unless `navigator.storage.persist()` is granted. That call applies to the origin, so it helps either approach.
- **Debugging is harder.** The DevTools IndexedDB viewer is less direct than reading localStorage keys.

## Important caveat: the tree has a limit too

Icon deduplication leaves the tree as the next limit. A link is roughly 200 characters with its id, title, and URL, so 5 MB holds around 25,000 links. That is a rough estimate, but it means moving only the icons does not remove the ceiling for very large libraries.

## Options

1. **Keep localStorage** if your measurements show you stay well under the limit. The current design is simpler.
2. **Icons only in IndexedDB.** This is a common middle ground. The tree stays synchronous, and icons load asynchronously per row, so the tree appears at once while icons fill in. The cost is that the tree and icons are no longer written atomically.
3. **Everything in IndexedDB.** This has the most benefit and the most rework. It is worth it if libraries get large.

My recommendation is to measure first with the console statistics. If you stay under about half the limit, keep localStorage. If you approach it, option 2 gives most of the benefit for the least change.

For this app, `idb-keyval` is the better fit. Our data is a few keyed values that the app loads into memory at startup, so we never need queries, indexes, or schema migrations. `idb` is more capable, but most of that power would go unused.

## What each library offers

**`idb-keyval`** (v6.3.0, about 300 bytes gzipped for `get`/`set`)
- A promise-based key-value API: `get`, `set`, `setMany`, `getMany`, `update`, `del`, `delMany`, `clear`, `keys`, `values`, `entries`.
- Values can be any structured-cloneable data, including `Blob`s.
- `createStore(dbName, storeName)` lets you name your own database instead of the default `keyval-store`.
- `setMany` is atomic. If one pair fails, none are written.

**`idb`** (v8.0.4, about 1.2 kB brotli)
- A thin wrapper over the full IndexedDB API. Requests become promises, and it adds `db.get`/`db.put` shortcuts.
- Supports multiple object stores in one transaction, indexes, cursors, async iteration, and `upgrade` hooks for schema changes.
- Typed schemas through `DBSchema`.
- You manage transactions yourself. Awaiting anything other than IndexedDB requests inside a transaction closes it.

## Fit for this app

Here is what we need, mapped to the two libraries:

- **Key-value storage** for a `tree` value and one entry per icon. Only `idb-keyval` is needed for this.
- **Atomic tree and icon writes.** `idb` can do this across two stores in one transaction. With `idb-keyval`, you can put both in one store, using a `tree` key and `icon:<id>` keys, and write them together with `setMany`.
- **Icon-only blobs.** Both store `Blob`s directly, so the base64 overhead goes away either way.
- **Ordering.** Overlapping read-write transactions run in the order they were created, so writes issued one after another land in order. Neither library needs an extra queue for that.
- **Queries and indexes.** We don't need them. The tree is loaded whole, and the atoms handle lookups in memory. This is the main reason to pick `idb` later.

Startup becomes async with either library, so the atom initialization and the first render need the same rework.

## Recommendation

Use `idb-keyval` with a custom store, for example `createStore("tmarks", "bookmarks")`. Store the tree under a `tree` key and each icon under `icon:<id>`, and save changes with `setMany`. This keeps the code close to the current `get`/`set` calls and keeps the tree and icons atomic.

Switch to `idb` only if one of these becomes true:

- You want to query without loading everything, for example icons or links by folder or URL.
- You want separate stores for nodes and icons with transactions across both.
- You need schema upgrades that move data between stores.

The export still needs base64 `ICON` strings. If icons are stored as `Blob`s, the export has to read each blob and convert it, so it becomes asynchronous. That is true with either library.
